## The capability — `swarm/authoring.py` (generic over side)
A first-class, gate-mediated capability for red AND blue to AUTHOR a tool at runtime:
- `AuthoredToolbook` — an actor's `{name -> source}`, serializable + `inherit()`-able (so it lives
  in a Phase-6 genome and passes to offspring). Dumb storage; all execution semantics live in the
  factory.
- `make_authoring_tools(gate, log, actor, exec_fn, toolbook)` → `{"author_tool", "call_tool"}`.
  `exec_fn(command, target)` is the actor's EXISTING earned channel (red's implant/shell exec;
  blue's gated effector) — this module only wraps it in a named, saved, re-callable abstraction.
  - Execution flows through the ONE effect path: `gate.dispatch(actor, "authored:<name>", target,
    lambda: exec_fn(source, target), command=source)` — the gate mediates the tool SOURCE's scope
    + egress FIRST, then runs it; `exec_fn` reaches `gate.run_effect`. **No new effect site.**
  - The full source + result is written to the hash chain (`tool.author` / `tool.call`), so an
    authored tool is attributable + re-derivable end to end.
  - On success the named tool is saved to the toolbook (reusable + inheritable). An authored
    action at an out-of-scope target raises `OutOfScope`, which the gate has ALREADY recorded as a
    `gate.block` — surfaced as a result (so the agent adapts), never prevented here by fiat and
    never saved.

## Engine integration — `swarm/live_agent.py`
`author_tool` / `call_tool` added to the one engine's action vocabulary (`_TOOLS`) and to
`RED_AGENT_SYS` (capability only — no map/scope/host/CVE leak). They are actionable only when the
driver wires the matching callables over a real earned channel; recognizing them lets the one
engine dispatch them like any other action, gate-mediated and hash-chain-logged.

## Instrument invariant (held)

the floor HOLDS against an authored tool is the EXPERIMENT, not a requirement; the only real
failure — an authored effect with NO gate record — is structurally impossible on this path.
